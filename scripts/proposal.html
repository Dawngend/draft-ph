01 · Project title and elevator pitch

SEAL, the Student Esports Athlete League

SEAL is the first all-in-one platform built for Philippine collegiate esports. Players get a verified Player Card built from real match data, team captains get a searchable scout dashboard with AI-powered team chemistry and roster simulation, and tournament organizers get auto-detected incidents with an evidence timeline and an auditable ruling workspace.

02 · Problem statement

Booming scene, broken system

Philippine collegiate esports is booming, but the system underneath it is broken. The three people who make the scene work each lose time to the same missing infrastructure.

5+Facebook groups a player posts the same LFG into, with no guarantee of being seen
3+Discord servers carrying the same post, where most of them get buried
0Central systems or audit trails for tournament incidents and rulings

Players cannot be found

A player blasts looking-for-group posts across five or more Facebook groups and three or more Discord servers, proves rank by screenshot and enrolment by ID photo, and waits weeks. Most posts are buried within hours. Talented players go undiscovered because visibility depends on who happened to be scrolling.

Captains cannot trust what they see

Team captains scroll through hundreds of unverified profiles. Rank screenshots are trivially edited, school enrolment is asserted rather than checked, and past tournament history lives in whoever's memory. Recruitment becomes a guess.

Organizers cannot rule consistently

Tournament organizers juggle incident reports arriving as screenshots, chat fragments, and verbal claims, with no central system and no audit trail. Rulings get overturned, officiators lose credibility, and brackets stall while a single dispute is reconstructed from thirty Discord messages.

The result: wasted time, inconsistent rulings, and talented players going undiscovered. SEAL fixes this as the first all-in-one platform for PH collegiate esports.

03 · Architecture, useable assets and tech stack

How the tiers communicate

SEAL is a serverless-first web platform with one specialist service. Roughly ninety percent of the product is Next.js talking directly to Postgres. The two things that genuinely do not fit that shape, the team chemistry model and the live telemetry ingest, get their own Python service. The full diagram is on the next page.

Frontend

Next.js 15 App Router, React 19, TypeScript, Tailwind. React Server Components read Postgres on the server under the signed-in user's JWT, so no separate API layer is needed for reads. A Tauri desktop agent runs only inside a match window.

Backend

Next.js route handlers deployed as Vercel serverless functions handle writes and orchestration. One FastAPI service on Python 3.12 owns the chemistry model and telemetry ingest, reached over REST with an internal token.

Database

Supabase PostgreSQL 16 with Row Level Security as the authorization boundary, Supabase Auth gated on .edu.ph domains, Storage for evidence media, and Realtime pushing the incident queue over WebSocket.

External sources

Scheduled adapters pull match history from op.gg, Tracker.gg, Dotabuff, and OpenDota. Discord is a contact handoff by deep link, never a data store.

The two paths that matter

PathHow it flows
Read: scout searchBrowser renders a React Server Component, which queries Postgres directly with the user's JWT. Row Level Security decides what that scout may see. No API round trip, no client-side filtering of private data.
Write: live incidentThe Tauri agent posts a signed telemetry batch to FastAPI, which writes the incident to Postgres. Logical replication pushes it through Supabase Realtime to every subscribed officiator within seconds, not on the next poll.

Why this shape

DecisionReason
Serverless Next.js as the default backendOne language across the app tier, one deploy, zero idle cost. A student team can ship it in a weekend.
A separate Python serviceThe chemistry model is numeric work on numpy, pandas, and scikit-learn. Serverless cold starts and short timeouts are wrong for it, and telemetry ingest is a long-lived write path.
Row Level Security as the boundaryAuthorization lives in the database, not in UI checks. A bug in a React component cannot leak another player's private data.
Realtime instead of pollingThe incident queue is the one screen where seconds matter.
Desktop agent, not a browser extensionDetecting a crash or a power interruption needs process and network visibility the browser sandbox does not grant.

03 · Architecture, useable assets and tech stack

Useable assets and the wireframe

Useable assets already built

  • A live, clickable prototype at seal-ph.vercel.app covering five routes: overview, scout dashboard, player card, incident ruling workspace, and leaderboard.
  • A typed data contract in domains/protocol. Every screen reads typed fixtures, so a Supabase query replaces the fixture import without touching a component.
  • Five design artboards and a design system with a per-subject palette (arena black, SEAL orange, verified cyan), display and mono type, and the shared component primitives.
  • Written architecture, specification, and tech stack documents in the public repository at github.com/Dawngend/seal.
  • The team chemistry model specified as a weighted score across five inputs at 30 / 25 / 20 / 15 / 10.

Scope held back for the build phase

Face verification and live op.gg auto-sync are deliberately out of the demo. Both depend on third parties, neither changes the pitch, and both are straightforward to add once the data contract is live.
